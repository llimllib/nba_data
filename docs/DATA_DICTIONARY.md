# NBA Data Dictionary

The data is one parquet file per dataset per season at
`https://basketball-data.billmill.org/nba/`, queried through the
[catalog](#v2-catalog-nbanbaduckdb). Start there. Men's college basketball is
separate, under `ncaam/` with its own catalog; see
[v2 College Basketball](#v2-college-basketball-ncaam).

The v1 files that used to be in this repo's `data/` directory were removed
when v2 replaced them ([#50](https://github.com/llimllib/nba_data/issues/50)).

## Season Naming Convention

Season years represent the **end** of the season (e.g., `2025` = 2024-25 season).

Data coverage:
- stats.nba.com data: 2009-10 season (2010) through current
- ESPN data: 2018-19 season (2019) through current

## v2 Schema Conventions

These rules apply to the v2 dataset in the `basketball-data` Space
(milestone "v2: object storage & a coherent dataset").

### Keys

Every table uses NBA ids as keys, with the same name and type everywhere
(except the college data under `ncaam/`, which has no NBA ids):

| Column | Type | Example | Notes |
|--------|------|---------|-------|
| `game_id` | VARCHAR | `0022500130` | 10 characters, zero-padded; see [NBA Game ID Format](#nba-game-id-format) |
| `player_id` | VARCHAR | `1629027` | NBA person id |
| `team_id` | VARCHAR | `1610612737` | NBA team id; see [Teams](#teams) |
| `season` | INTEGER | `2026` | End year of the season (2026 = 2025-26) |

Ids are identifiers, not numbers, so they are all strings: no arithmetic, no
loss of leading zeros, no overflow if the NBA issues a larger id. They are
stored exactly as the NBA publishes them. Sources that return ids as numbers
are converted directly from integer to string, never through a float (which
would produce `1629027.0`). `season` stays an INTEGER because it is used in
arithmetic and ranges.

Columns that refer to another team or player end in `_team_id` or
`_player_id` and hold the same ids (`opp_team_id`, `home_team_id`,
`assist_player_id`). The integrity check finds key columns by these names.

Source-specific names for these keys (`gameId`, `gmId`, `personId`, `plyrID`,
`teamId`, `tmID`, ...) are renamed when the parquet is written.

### Teams

A `team_id` is a franchise as the NBA defines it, not a name. For example,
`1610612766` covers the 1988-2002 Charlotte Hornets, the Charlotte Bobcats, and
the current Charlotte Hornets, while `1610612740` covers the New Orleans
Hornets and the Pelicans.

- **Joining:** a team's name and abbreviation for a given row come
  from joining `team_seasons` on `(team_id, season)`. A 2013 Charlotte game
  shows "Bobcats" and a 2016 one shows "Hornets" with no special cases.
  `team_seasons` is generated from the NBA game logs, so renames, All-Star
  teams and exhibition opponents appear automatically.
- **Ingesting:** a source that identifies teams only by abbreviation is resolved
  through `pipeline/team_abbrevs.csv`, a hand-maintained
  `(source, abbrev, first_season, last_season) -> team_id` table. An unknown
  `(source, abbrev, season)` fails the run. Sources with their own team ids
  use it too, with the id as the abbreviation (`ctg`, and `espn_team_id`,
  the ids in ESPN's site API).
- **Players from other sources:** a source with its own player ids
  (basketball-reference's `jamesle01`) is resolved through
  `pipeline/player_ids.csv`, `(source, source_id) -> player_id`, with a
  `method` column saying how each was found: `name_team` (same normalized
  name on the same team that season), `name_season`, `player_page` (the
  source's page links to the NBA id) or `manual`. Generated by
  `python -m pipeline.player_ids`, which never changes existing rows. A
  bbref player with no mapping fails the run. ESPN's season net points
  files use ESPN's ids: they're matched by a unique name in the season's
  `player_seasons` at build time, with `espn` rows in `player_ids.csv` (all
  `manual`) for the few names that don't match. EPM, Cleaning the Glass and
  ESPN's daily files already use NBA ids.
- NBA abbreviations are not unique within a season (in 2026 `MEL` is both
  Melbourne United and the All-Star Team Melo), another reason they are never
  keys.
- Abbreviations and team names are never stored in data tables. They live only
  in `team_seasons` and `team_abbrevs.csv`.

### Columns

- Column names are snake_case and never start with a digit (ESPN's
  `2pt_oNetPts` becomes `fg2_o_net_pts`)
- Numeric columns are INTEGER, DOUBLE, or BIGINT only when a value needs it.
  DuckDB-wasm returns BIGINT as a JavaScript BigInt, which Observable Plot
  can't handle
- `game_date` is a DATE, the date the NBA lists for the game (US Eastern)
- Yes/no values are BOOLEAN
- Missing values are NULL, never `0` or `''`

### Types

Types in this document are DuckDB types, since DuckDB writes the parquet
files. They map to parquet like this (checked with `parquet_schema()`):

| DuckDB | Parquet physical type | Parquet annotation | pyarrow / polars |
|--------|-----------------------|--------------------|------------------|
| VARCHAR | BYTE_ARRAY | UTF8 | string / String |
| INTEGER | INT32 | INT_32 | int32 / Int32 |
| BIGINT | INT64 | INT_64 | int64 / Int64 |
| DOUBLE | DOUBLE | (none) | double / Float64 |
| BOOLEAN | BOOLEAN | (none) | bool / Boolean |
| DATE | INT32 | DATE | date32 / Date |

Files are compressed with zstd. DuckDB (including DuckDB-wasm), pyarrow,
polars and pandas read it; some lightweight JavaScript readers need an add-on
(hyparquet needs `hyparquet-compressors`).

### Where normalization happens

All of the above is applied when parquet files are written, not in the catalog
views. Reading a parquet file directly gives the same clean data as querying
through `nba.duckdb`.

### Layout

```
nba/raw/<source>/<season>/...                        raw responses, gzipped
nba/<source>/<dataset>/season=<season>/data.parquet  one file per season
nba/nba.duckdb                                       the catalog
nba/metadata.json                                    the catalog's metadata table, as JSON
ncaam/...                                            college basketball, laid out the same
ncaam/ncaam.duckdb                                   its catalog
ncaam/metadata.json                                  its metadata table, as JSON
```

The season is in the path (Hive partitioning) so that a query filtered on
`season` only opens that season's files. One side effect: DuckDB reads
`season=2026` from the path even for a single file, and types it BIGINT,
replacing the file's own INTEGER `season`. To keep it an INTEGER when
reading files directly, pass `hive_types = {'season': INTEGER}` (or
`hive_partitioning = false`) to `read_parquet`. The catalog's views do this
already.

Finished seasons are never rewritten; each run rewrites only the current
season. That includes the lookup tables (`team_seasons`, `player_seasons`,
`games`), which are per season like everything else; the catalog combines
them.

## v2 Catalog (`nba/nba.duckdb`)

A small DuckDB database of views over every season's parquet files, rebuilt
every run by `pipeline/catalog.py`, so new seasons appear automatically:

```sql
ATTACH 'https://basketball-data.billmill.org/nba/nba.duckdb' AS nba;
SELECT p.name, round(s.pts, 1) AS ppg
FROM nba.player_season_stats_per_game s JOIN nba.players p USING (player_id)
WHERE s.season = 2026 AND s.season_type = 'regular_season' AND s.gp >= 50
ORDER BY ppg DESC LIMIT 10;
```

| Name | Type | Description |
|------|------|-------------|
| `team_game_logs`, `player_game_logs`, `player_season_stats`, `team_seasons`, `player_seasons`, `games` | view | Every season of each `nba/stats/` dataset |
| `schedule` | view | Every game on the schedule, played or not, from 2027 |
| `rosters_daily` | view | Every team's roster as of each day fetched, from 2027 |
| `game_rotations`, `game_events`, `player_game_status` | view | Each game's player stints, play-by-play, and every player in its box score (and, from November 5, 2026, its inactive players) with why they didn't play, for seasons with play-by-play |
| `four_factors`, `player_box`, `team_box`, `player_details`, `net_pts_season` | view | Every season of each `nba/espn/` dataset |
| `espn_injuries` | view | ESPN's injury list as of every fetch, from 2027 (`nba/espn/`) |
| `betting_lines` | view | Each game's opening and closing spread, total and moneylines by sportsbook or archive, from 2012 (`nba/espn/`) |
| `bbref_team_stats`, `bbref_salaries` | view | Every season of basketball-reference's team stats and player salaries (`nba/bbref/`) |
| `ctg_team_summary` | view | Every season of Cleaning the Glass's team summary (`nba/ctg/`) |
| `epm`, `epm_predictive` | view | dunksandthrees' season and predictive EPM, from 2026 (`nba/dunksandthrees/`) |
| `epm_daily`, `epm_predictive_daily` | view | The same as of every day fetched, from 2027 |
| `team_epm`, `team_epm_daily` | view | dunksandthrees' team ratings, the latest day and every day fetched, from 2027 |
| `openrapm` | view | OpenRAPM player ratings, from 2010 (`nba/openrapm/`) |
| `team_openrapm`, `team_openrapm_daily` | view | OpenRAPM's team power ratings, the latest day and every day, from 2027 |
| `players` | table | One row per `player_id`: `name` (the latest one known), `first_season`, `last_season` (seasons on a roster count, even without games). A table, so joining it reads no parquet files |
| `player_season_stats_per_game`, `player_season_stats_per_36`, `player_season_stats_per_100` | view | `player_season_stats` with counting stats scaled; see below |
| `metadata` | table | Per dataset: `source`, `first_season`, `last_season`, `seasons`, and `updated`, when its newest file was uploaded |

**Without DuckDB:** the `metadata` table is also published as
`nba/metadata.json` (and `ncaam/metadata.json`), built and uploaded with the
catalog, for clients that read the parquet files directly (hyparquet,
pyarrow) and need to know which seasons exist. It has the table's rows, keyed
by dataset, with `updated` in UTC ISO 8601:

```json
{
  "datasets": {
    "games": {"source": "stats", "first_season": 2010, "last_season": 2027, "seasons": 18, "updated": "2026-10-24T14:42:21Z"}
  }
}
```

`seasons` is a count: a dataset has a gap if it's less than
`last_season - first_season + 1`. None has one.

Views read their files with hive partitioning, so filtering on `season`
only downloads the files for those seasons; other filters (`player_id`,
`game_id`) still read every season's file. Filter on `season` whenever you
can. If a column is ever added in a later season, that dataset's view reads
with `union_by_name` instead, which makes the column NULL in earlier seasons
but opens every file.

**In the browser (DuckDB-wasm):** use DuckDB-wasm 1.32 or later and switch
to the httpfs extension before attaching:

```sql
SET builtin_httpfs = false;
LOAD httpfs;
ATTACH 'https://basketball-data.billmill.org/nba/nba.duckdb' AS nba;
```

DuckDB-wasm's built-in HTTP backend sends a request to every season's file
before each query and downloads whole files instead of the parts it needs
([duckdb/duckdb-wasm#2228](https://github.com/duckdb/duckdb-wasm/issues/2228)).
With httpfs, a one-season query takes about 1.7s cold, against 4-8s
without. Native DuckDB (CLI, Python) needs none of this.

**Precision:** the per-mode views return full-precision values
(`13.20481004041412`). Round when displaying, and when writing results to a
file (e.g. a data loader), round to the precision you need and keep only the
columns you use: full-precision doubles compress badly. nba0bservable's
player stats loader went from 5.8MB to 1.85MB by rounding to one decimal and
writing zstd.

**Integrity:** the catalog is only published if every key matches the lookup
tables. Every non-NULL `team_id`/`*_team_id` is in `team_seasons`, every
`player_id`/`*_player_id` in `player_seasons`, and every `game_id` in `games`,
all for the row's season. Each `games.game_id`'s season digits also match its
`season`. So joining any table to a lookup on `(season, <key>)` never drops
rows. The exception is `schedule`, which lists games and teams before
they've played.

## v2 NBA Stats Data (`nba/stats/`)

Built by `pipeline/stats.py` from stats.nba.com, except `game_rotations`,
`game_events` and `player_game_status` (`pipeline/rotations.py`, below). Each run refetches the whole current
season (14 requests, plus 1 for `schedule`), so stat corrections the NBA makes after
games are picked up. Raw responses are kept at
`nba/raw/stats/<season>/<request>.json.gz`. Team rosters (30 requests, for
`player_seasons` and `rosters_daily`) are refetched once a day, into
`nba/raw/stats/<season>/team_rosters.json.gz`, and each day's are kept at
`nba/raw/stats/<season>/team_rosters/<date>.json.gz`.

Columns are the NBA's names, lowercased. Names and abbreviations are dropped
(use the lookup tables), as are the `*_rank` columns (use `rank() OVER
(...)`). Counting stats are INTEGER and other numbers DOUBLE, set by column
name: the NBA sometimes sends counts as floats.

**Known gaps:** the game log endpoints omit some All-Star weekend exhibitions
(4 games in 2025-26, such as the Rising Stars games), and player game logs
only include players who played; DNPs aren't listed. Players with no NBA id
(seen on international teams in preseason exhibitions) are skipped.

### `team_game_logs/season=<season>/data.parquet`

One row per team per game, for every game type (preseason through the
finals). The NBA's traditional and advanced team box scores, joined.

| Column | Type | Description |
|--------|------|-------------|
| opp_team_id | VARCHAR | The other team in the game |
| game_date | DATE | |
| home | BOOLEAN | NULL for neutral-site games, where the NBA lists both teams as away |
| win | BOOLEAN | |
| min, fgm, fga, ..., pts | | Traditional box score |
| plus_minus | INTEGER | Points minus the opponent's points. Computed, not the NBA's value, which is wrong in 9 preseason games (once 4.4) |
| off_rating, def_rating, net_rating, pace, poss, pie, ... | | Advanced box score; `e_` columns are the NBA's estimates |
| team_oreb | INTEGER | Team offensive rebounds, which `oreb` doesn't count (below). From `game_events`; NULL for a game whose play-by-play we don't have |

`poss` is counted from the play-by-play, not estimated from the box score.
A possession ends when the other team gets the ball, and the team that gets
the ball after a period ends on a make, a turnover or made free throws is
credited with one, even if it never runs a play. That's why a team's `poss`
and its opponent's differ by at most 4. Counting this way from
`game_events` reproduces `poss` exactly in 80% of 2025-26 regular-season
team games and within one in 99%. The season total comes within 12 of
NBA.com's 246,200.

`poss` is 1-3% below the textbook formula, `fga + 0.44 * fta + tov - oreb`
(1.8 a game in 2025-26). Most of that is team offensive rebounds. The box
score's `oreb` counts only player rebounds. A miss that goes out of bounds
off the defense is a team rebound: it's in `game_events` (a `Rebound` with no
`person_id`, by the shooting team), and the possession continues, but the
formula counts a new one. Teams that crash the glass get more of them, so the
gap differs by team: in 2025-26 it ran from 1.1% (OKC) to 3.2% (CHA) of
possessions. `team_oreb` counts them, and `fga + 0.44 * fta + tov - oreb -
team_oreb` is 0.8% to 1.4% below `poss` for every team. It counts a team
rebound after the team's own miss when the team's next shot, free throw or
turnover is in the same period. That's mostly live second chances, plus
shot-clock violations (recorded as a team rebound, then a turnover). It
leaves out team rebounds on a miss as a period ends, since the period ends
either way, and the dead-ball "rebounds" between free throws.

### `player_game_logs/season=<season>/data.parquet`

One row per player per game they played in, with the same traditional and
advanced columns as the team logs plus usage (`usg_pct`), fantasy points and
`dd2`/`td3`. `opp_team_id` and `home` come from the team's game log.

### `player_season_stats/season=<season>/data.parquet`

One row per player per `season_type` (`regular_season` or `playoffs`):
season **totals** from the NBA's Base, Defense and Advanced player stats,
2-point shooting, and bio data. A player traded mid-season has one row;
`team_id` is their last team.

Per-mode stats are computed from the totals, which reproduces the NBA's
PerGame, Per36 and Per100Possessions values within their rounding. The
catalog's `player_season_stats_per_game`, `_per_36` and `_per_100` views do
this: they have the same columns as `player_season_stats`, with the counting
stats (`pts`, `fgm`, `reb`, `def_ws`, ...) scaled. Rates, ratings, `gp`, `w`,
`l`, `dd2`, `td3` and `poss` aren't scaled, and `min` is only scaled per game
(the NBA's per-36 and per-100 modes keep total minutes). A zero denominator
gives NULL. Formulas:

| Mode | Formula |
|------|---------|
| Per game | `total / gp` |
| Per 36 minutes | `total / min * 36` |
| Per 100 possessions | `total / poss * 100` |

For defensive win shares use `def_ws_raw`; `def_ws` is rounded to 2
decimals, which distorts per-mode values for low-minute players. The per-mode
views compute `def_ws` from `def_ws_raw` when it's present.

| Column | Type | Source |
|--------|------|--------|
| gp, w, l, min, pts, ... | | Base |
| def_rating, def_ws, def_ws_raw, opp_pts_paint, ... | | Defense |
| off_rating, usg_pct, ts_pct, poss, pie, ... | | Advanced |
| fg2m, fg2a, fg2_pct, fga_frequency, ... | | 2-point shots; NULL for players with no 2-point attempts |
| player_last_team_id | VARCHAR | 2-point shots |
| player_height, player_height_inches, player_weight | VARCHAR, INTEGER, INTEGER | Bio |
| college, country | VARCHAR | Bio |
| draft_year, draft_round, draft_number | INTEGER | Bio; NULL if undrafted |

### `game_rotations/season=<season>/data.parquet`

One row per player stint: each time a player checked in and out of a game,
with their points and the score change while they were on the floor. For
rotation charts. Built by `pipeline/rotations.py` from each game's
play-by-play (`playbyplayv3`) and box score (`boxscoretraditionalv3`),
fetched incrementally (only new games and the last two days') and kept at
`nba/raw/stats/<season>/playbyplay/<game_id>.json.gz`. Updated daily by
`sources.yml`. Every game type is covered, preseason through the finals.

A stint runs from a substitution to the next one, across period breaks: a
player who plays the end of the 1st quarter and the start of the 2nd has
one row. A player subbed out and back in at the same moment has two rows,
one ending and one starting at that time. Stints can be very short, from
substitutions during free throws.

Free throws count for the players who were on the floor for the foul
(unless a player subbed in shoots them, for an injured or ejected player),
and technical free throws for the players on when the technical was
called (except flopping technicals', which count for the players on when
they're shot), as in the NBA's box score plus-minus. The score is counted from the made
shots and free throws rather than read from the play-by-play, whose scores
are sometimes wrong.

| Column | Type | Description |
|--------|------|-------------|
| season, game_id, team_id, player_id | | Key: `(game_id, player_id, in_time)` |
| period | INTEGER | The period the stint starts in: 1-4, 5 for the first overtime, and so on |
| in_time, out_time | DOUBLE | Seconds from the start of the game, to the tenth: 720 is the end of the 1st quarter, 2880 the end of regulation, and each overtime is 300 |
| pts | INTEGER | The player's points in the stint |
| plus_minus | INTEGER | The team's points minus the opponent's while the player was on the floor |
| matches_box_score | BOOLEAN | Whether the game's stints add up to the box score (see below). The same for every row of a game |

**Known problems:** the NBA's play-by-play is sometimes wrong: a missed
substitution leaves a player on the floor after they left, or a game's
plays are in the wrong period. The build checks every game, and a game
whose stints don't add up to each player's plus-minus and minutes, with
five players a side, has `matches_box_score` false. Filter on it for
charts. The NBA's two box scores (`player_game_logs` and the game's box
score) sometimes disagree about a player's plus-minus; matching either
counts. Of 440 games checked (2010-2027, every game type), 437 match, and
2,777 of the 2,787 in 2025-2027. The 2025 All-Star games, played to a
target score with no game clock, have no rows.

### `game_events/season=<season>/data.parquet`

One row per action in the play-by-play (shots, free throws, rebounds,
fouls, turnovers, steals, blocks, substitutions, timeouts, jump balls,
violations, replays, period starts and ends), with the score after it.
Filter on `pts > 0` for the scoring plays, for score-margin (worm)
charts. Built with `game_rotations`, from the same play-by-play, and the
score is counted the same way, from the made shots and free throws, so
each team's points add up to its stints' `pts` and the last scoring row
has the final score.

The two tables put free throws at different moments. Here each play is
at the time it happened, in the play-by-play's order. `game_rotations`
counts free throws for the players on for the foul, so its plus-minus
can include free throws shot after a substitution on the same clock
tick. A basket on that tick that's listed after the substitution is also
the new lineup's. So the score at a stint's `in_time` (the last row with
`time <= in_time`) can differ from the score the stints imply there, but
only by scoring plays on that same tick: in 2026-2027, that's 655 of
215,542 stint boundaries, 607 of them free throws alone.

| Column | Type | Description |
|--------|------|-------------|
| season, game_id | | Key: `(game_id, action_id)` |
| action_id | INTEGER | The action's place in the play-by-play (`actionId`), which orders actions on the same clock tick |
| action_number | INTEGER | The play-by-play's `actionNumber`, which repeats within a game: a steal or block shares it with the turnover or missed shot it goes with |
| period | INTEGER | 1-4, 5 for the first overtime, and so on |
| time | DOUBLE | Seconds from the start of the game, to the tenth, on `game_rotations`' clock: 720 per period, 300 per overtime. Null for games with no game clock (the 2025 All-Star games) |
| team_id | VARCHAR | The action's team. The NBA puts team actions' (team rebounds, timeouts) team in their person id; here it's in `team_id`. Null for period starts and ends, replays, coaches' technicals and ejections, and heaves (end-of-period team shots, whose team is only in the description), and the NBA leaves out a few others (in 2023-2027, 29 blocks and 2 turnovers) |
| person_id | VARCHAR | Who did it: usually a player (with the id `player_game_logs` uses), but the coach for a coach's technical or ejection, and an unexplained small number for instant replays. Null for team actions |
| action_type | VARCHAR | `Made Shot`, `Missed Shot`, `Free Throw`, `Rebound`, `Foul`, `Turnover`, `Substitution`, `Timeout`, `Jump Ball`, `Violation`, `Ejection`, `Instant Replay`, `Heave`, `period`. Steals and blocks have none (the NBA leaves it empty): their `description` has `STEAL` or `BLOCK` |
| sub_type | VARCHAR | The kind of action: the shot type, the foul type (`Shooting`, `Personal`, `Offensive Charge`, `Technical`, ...), the turnover type, `start` or `end` for periods |
| description | VARCHAR | The NBA's text, which has what other columns don't: who assisted, who drew a foul or got the steal, the referee, foul counts (`P2.T3`: the player's second foul, the team's third of the period) |
| shot_result | VARCHAR | `Made` or `Missed`, for shots and free throws (the NBA leaves free throws' empty; here it's from the description, as the score is) |
| is_field_goal | BOOLEAN | Whether it's a shot from the field |
| shot_value, shot_distance, x, y | INTEGER | For shots from the field: 2 or 3, the distance in feet, and the location (the NBA's `xLegacy` and `yLegacy`, in tenths of a foot from the basket) |
| video_available | BOOLEAN | Whether the NBA has video of it |
| pts | INTEGER | The points it scored: 0, 1, 2 or 3 |
| home_team_id, away_team_id | VARCHAR | The box score's home and away teams, which `home_score` and `away_score` are for. Neutral-site games, which have none in `games`, have them here too |
| home_score, away_score | INTEGER | The score after this action |
| matches_box_score | BOOLEAN | `game_rotations`' flag for the game: whether its stints add up to the box score. A game's scoring can be right when its stints aren't (a missed substitution doesn't change the score); the site filters on it to match the rotations it shows. Null for games with no game clock, which have no stints |

Sorted by `game_id` and `action_id`, in row groups of 16,384 rows (about
32 games), so reading one game by `game_id` reads one row group: for 2026
(703k rows, 11MB), a 106KB footer and, for the scoring columns, 43KB of
rows. In hyparquet the filter must use an operator (`{game_id: {$eq: id}}`)
to skip row groups, and its default first read is the file's last 512KB,
so pass a smaller `initialFetchSize` (128KB) to read only the footer.

### `player_game_status/season=<season>/data.parquet`

Every player in each game's box score, whether they started and played,
and, for those who didn't play, why: the box score's comment (`DNP -
Coach's Decision`, `Inactive - Injury/Illness`), split into a status and
a reason. From November 5, 2026 on, it also has the players on each
team's roster that day who aren't in the box score, as `inactive`. It's
what happened, known after the game, not the pre-game injury report
(that's `espn_injuries`). Built from the box scores saved with
`game_rotations` (`boxscoretraditionalv3`), for the same games.

The box scores usually leave out the players on the inactive list. They
list players who were active and didn't play (`DNP`), didn't dress
(`DND`) or weren't with the team (`NWT`). For one week, the 2027 games
from October 20 to 26, 2026, they listed inactive players too, with a
reason (`Inactive - Injury/Illness`). The NBA stopped on about October
27, and dropped them from those games' box scores as well when they were
fetched again. So since then, inactive players come from
`rosters_daily`: a player on the team's roster that day (the latest saved
rosters on or before the game's date) who isn't in either team's box
score is `inactive`, with a NULL `reason` and `in_box_score` false. The
reason, when there is one, is in `espn_injuries`. Rosters were first
saved on November 5, 2026, so 2027 games from October 27 to November 4
(69 regular-season games) and every earlier season have no inactive
players: a player missing from a game's rows isn't necessarily off the
team.

Players who didn't play and aren't in that season's `player_seasons` are
left out: before 2027 `player_seasons` only has players who got on the
floor that season, so a player who never did (2021-22's hardship
signings, say) would fail the integrity check. That's 50 rows in
2018-2026; the build lists them.

| Column | Type | Description |
|--------|------|-------------|
| season, game_id, team_id, player_id | | Key: `(game_id, player_id)` |
| starter | BOOLEAN | Started the game (the box score gives starters a position) |
| played | BOOLEAN | Got on the floor: has minutes, or has no comment. A few players in for no time (`0:00`, on for a free throw or the last second) have no comment, and count; they have no stint in `game_rotations`, since a stint with no time is folded away. From the minutes rather than the comment because a few 2027 box scores say `DNP - Coach's Decision` for a player with minutes |
| status | VARCHAR | `played`, or for players who didn't: `dnp` (active, didn't play), `dnd` (didn't dress), `nwt` (not with the team), `inactive` (on the inactive list: in the box score October 20-26, 2026, and from the rosters from November 5, 2026). Null for a comment the build doesn't know (it lists them) |
| reason | VARCHAR | Null for players who played, and for inactive players from the rosters. Otherwise `coach` (coach's decision), `injury` (injury or illness), `concussion_protocol`, `reconditioning` (return to competition reconditioning), `health_and_safety` (COVID protocols and self-isolation, 2020-2022), `rest`, `personal`, `not_with_team`, `g_league_two_way` (only October 20-26, 2026), `league_suspension`, `team_suspension`, `suspension` (2018-2019, which don't say whose), `ineligible` (ineligible to play), `trade` (a trade pending or just made). | in_box_score | BOOLEAN | False for inactive players from the rosters |

```sql
-- why a team's players missed games this season
SELECT p.name, s.reason, count(*) AS games
FROM player_game_status s
JOIN players p USING (player_id)
JOIN team_seasons t USING (season, team_id)
WHERE s.season = 2027 AND t.nba_abbrev = 'BOS' AND NOT s.played
GROUP BY ALL ORDER BY games DESC;
```

### `schedule/season=<season>/data.parquet`

Every game on the NBA's schedule for the season, played or not, from
`scheduleleaguev2` (one request, refetched every run, so postponements and
new times are picked up). Use it for upcoming games; for played games,
`games` and `team_game_logs` have the same `game_id`s. Raw response at
`nba/raw/stats/<season>/schedule.json.gz`. From 2027 (2026-27).

Differences from `games`:

- A game is listed before it's played, so its `game_id` and teams may not
  be in `games` or `team_seasons` yet. The integrity check skips this
  table's keys; the build checks that the ids are in the season and that
  only NBA teams play NBA games.
- At a neutral site, `home_team_id` and `away_team_id` are the teams the NBA
  lists as home and away, with `neutral_site` true. In `games` they're NULL.
- The Cup's knockout games (quarterfinals, semifinals, final) are listed
  with their `game_id` from the start of the season, with NULL teams until
  the matchups are set. In 2025-26 the same ids were played.
- The regular season fills in during the Cup: the games around its knockout
  round for the teams that aren't playing in it (24 in 2026-27) are
  scheduled once those teams are known, so until December there are fewer
  than 1,230 regular-season games. Playoff games appear as series are set.
- It has the All-Star weekend games the game logs leave out (Rising Stars),
  with their own teams, and in some past seasons it lacks preseason games
  (2019-20 has none).

| Column | Type | Description |
|--------|------|-------------|
| season, game_id | | Key |
| game_date | DATE | US Eastern, as in `games` |
| start_time | TIMESTAMPTZ | Tip-off as scheduled |
| game_type, playoff_round, series_number, series_game | | Decoded from the game id, as in `games` |
| home_team_id, away_team_id | VARCHAR | NULL until the teams are known |
| neutral_site | BOOLEAN | |
| status | VARCHAR | `scheduled`, `in_progress` or `final` |
| status_text | VARCHAR | The NBA's: `7:30 pm ET`, `Final`, ... |
| label, sub_label | VARCHAR | The NBA's labels: `Emirates NBA Cup` / `East Group A`, `NBA Finals` / `Game 6`, `Preseason`, `NBA Paris Game`, ... |
| subtype | VARCHAR | `in-season` (Cup group games) or `in-season-knockout` |
| series_text | VARCHAR | A playoff game's series score: `MIL leads 3-2` |
| if_necessary | BOOLEAN | A playoff game that's only played if the series isn't over |
| arena_name, arena_city, arena_state | VARCHAR | |

Not kept: scores and records (in `team_game_logs`), team names (use
`team_seasons`), broadcasters, and the times in other zones.

```sql
-- the next week's games
SELECT s.start_time, a.nba_abbrev AS away, h.nba_abbrev AS home, s.neutral_site
FROM schedule s
JOIN team_seasons h ON h.season = s.season AND h.team_id = s.home_team_id
JOIN team_seasons a ON a.season = s.season AND a.team_id = s.away_team_id
WHERE s.season = 2027 AND s.status = 'scheduled'
    AND s.game_date < current_date + 7
ORDER BY s.start_time;
```

### `rosters_daily/season=<season>/data.parquet`

Every NBA team's roster as of each day the rosters were fetched (once a
day), from `commonteamroster`, from 2027 (November 2026 on): one row per
`as_of_date`, `team_id` and `player_id`. It includes players who haven't
played (injured, say), so it's the place to find a team's full roster;
for a date, use the latest `as_of_date` on or before it. A day the fetch
failed is missing. Each team has 13 to 21 players during the season, two-way
contracts included; a fetch with fewer or more fails the run rather than
being published. Every `player_id` is in `player_seasons`. The file isn't
written until every rostered team has played a game that season (so is in
`team_seasons`).

| Column | Type | Description |
|--------|------|-------------|
| season, as_of_date, team_id, player_id | | Key. `as_of_date` is the day the rosters were fetched, US Eastern |
| num | VARCHAR | Jersey number (`00` isn't `0`); NULL if the NBA has none |
| position | VARCHAR | `G`, `F`, `C`, `G-F`, `F-C`, ... |
| two_way | BOOLEAN | The NBA's `SUPPLEMENTAL_STATUS` is 1: about three players a team, almost all with no salary in `bbref_salaries` (or one paid by a team that waived them), so two-way contracts |
| how_acquired | VARCHAR | The NBA's text: `Traded from OKC on 07/19/26`, `Signed on 09/14/26`, `#3 Pick in 2026 Draft` |

Not kept: names (use `players`), height, weight, age and school (in
`player_season_stats`), and the coaches.

```sql
-- each team's latest roster, with its two-way players last
SELECT t.nba_abbrev AS team, p.name, r.position, r.two_way
FROM rosters_daily r
JOIN players p USING (player_id)
JOIN team_seasons t USING (season, team_id)
WHERE r.season = 2027
    AND r.as_of_date = (SELECT max(as_of_date) FROM rosters_daily WHERE season = 2027)
ORDER BY team, r.two_way, p.name;
```

-- this season's conference standings, from the game logs

## v2 ESPN Data (`nba/espn/`)

Built by `pipeline/espn.py` from ESPN's net points data

table has `season`, `game_id` and `team_id`; player tables also have
`player_id`. Player and team names come from the lookup tables.

ESPN recomputes past seasons from time to time. Seasons 2019-2025 were
fetched in October 2026, after ESPN's latest recomputation, and match its

happened, so some hold values ESPN has since revised

### `net_pts_season/season=<season>/data.parquet`

ESPN's own season totals of net points, one row per player per game type,
built by `pipeline/espn_net_pts.py` from the two files at
`nfl-player-metrics.s3.amazonaws.com/net-pts/` (totals and per 100). Raw
files: `nba/raw/espn/net_pts/{totals,per_100}.json.gz`, latest only.

For 2019-2025 these equal sums of `player_box` exactly (net points, games
and team possessions; [#66](https://github.com/llimllib/nba_data/issues/66),
[#72](https://github.com/llimllib/nba_data/issues/72)). For 2026 they
differ for some players, because ESPN revised days after we saved them;
the totals here are ESPN's current values.

The current season is rewritten daily; finished seasons hold ESPN's values
as of their last run (all of 2019-2026 as of October 2026).

| Column | Type | ESPN field | Description |
|--------|------|------------|-------------|
| season, season_type, player_id | | min_season, seasonType, dot_com_id | Key. `season_type` is `regular_season`, `playoffs`, `play_in` or `cup_final`, as in `games.game_type`: the NBA Cup final isn't in the regular season |
| team_id | VARCHAR | tm | Latest team that season |
| gp | INTEGER | net_pts_games | |
| min | DOUBLE | totMin | |
| o_net_pts / d_net_pts / t_net_pts | DOUBLE | offense / defense / overall | `t = o + d` |
| o_team_poss / d_team_poss / t_team_poss | DOUBLE | oTmPoss / dTmPoss / tTmPoss | Team possessions on the court, `t = o + d` |

Per 100 possessions, as ESPN computes it: `o_net_pts / o_team_poss * 100`,
the same for defense, and total as the sum of the two (not
`t_net_pts / t_team_poss`).

### `betting_lines/season=<season>/data.parquet`

Betting lines for every game from 2012, one row per game and provider (a
sportsbook, or an archive), built by `pipeline/espn_odds.py`
([#99](https://github.com/llimllib/nba_data/issues/99)). Which providers a
season has:

| Seasons | `provider_id` | Lines |
|---|---|---|
| 2012-2022 | `sbr` | sportsbookreview.com's archive, as scraped by [flancast90/sportsbookreview-scraper](https://github.com/flancast90/sportsbookreview-scraper) (MIT): open and close spread and total, closing moneylines. Each season's last Finals game is missing (the scrape lost its home team) |
| 2020 (the bubble) to 2026 | `odds_api_consensus` | The Odds API's consensus close, the median across 9-19 books at the last snapshot before tip-off, from [sportsdataverse/hoopR-nba-data](https://github.com/sportsdataverse/hoopR-nba-data): close spread and total only |
| 2026 on | `100` (DraftKings), `58` (ESPN BET, until November 30, 2025) | ESPN's site API, every `update.yml` run: open and close spread, total, moneylines and all their prices |

Where two overlap they agree closely: in 2020's bubble, sportsbookreview's
and the Odds API's closing spreads were within a point in 168 of 172
games, and ESPN's books and the consensus within a point in 99% of 2026's.
Every game from 2012 to 2026 has a line except the last Finals game of
2012-2019 and one 2023 game (0022200219). For one closing line per game, prefer ESPN's book, then
the consensus, then `sbr`. ESPN's own odds for earlier seasons (many books,
2013 on) are missing for about half the games, so they weren't fetched.

The archives are kept as downloaded, from a pinned commit, at
`nba/raw/sbr/nba_archive_10Y.json.gz` and
`nba/raw/sportsdataverse/closing_lines_odds_api.parquet`.
sportsbookreview's has errors that are fixed on the way in: in about 7%
of games the closing spread and total are swapped (the favorite comes
from the moneylines), 2019-20's bubble games are dated a year early, and
impossible values (a 1955.5 total, a 0 moneyline) are NULL. ESPN's raw
files:

- `nba/raw/espn/<season>/scoreboard/<date>.json.gz`: each day's games
  (ESPN's event ids and teams), refetched until the day is 2 days old
- `nba/raw/espn/<season>/odds/<event_id>.json.gz`: the core API's odds for
  each game (`sports.core.api.espn.com/.../events/<id>/competitions/<id>/odds`),
  fetched once it's final. ESPN's scoreboard drops the odds when a game
  starts, but the core API keeps them

ESPN's and sportsbookreview's games are matched to the NBA's by teams and
date (a day either side is allowed, nearest first), against
`team_game_logs`, so a game's lines appear in the run after it's in
`games`. The Odds API's, keyed by ESPN event id, are matched through
ESPN's scoreboards. Preseason and All-Star games are left out. ESPN's
in-game ("Live Odds") lines are dropped.

| Column | Type | Description |
|--------|------|-------------|
| season, game_id, provider_id | | Key. `provider_id` is ESPN's id for the book (`100` is DraftKings), or `sbr` or `odds_api_consensus` |
| provider | VARCHAR | The book's or archive's name |
| home_team_id, away_team_id | VARCHAR | As the source designates them, at neutral sites too (where `games` has neither) |
| open_spread, close_spread | DOUBLE | The home team's spread: negative when it's favored. The home team covers when `margin + spread > 0` |
| open_total, close_total | DOUBLE | Over/under |
| open_home_moneyline, open_away_moneyline, close_home_moneyline, close_away_moneyline | INTEGER | American odds (`-324`, `261`) |
| open_home_spread_odds, open_away_spread_odds, close_home_spread_odds, close_away_spread_odds | INTEGER | The price of each side of the spread |
| open_over_odds, open_under_odds, close_over_odds, close_under_odds | INTEGER | The price of each side of the total |
| espn_event_id | VARCHAR | ESPN's id for the game; NULL for `sbr` |

`close_*` is ESPN's closing line; where a book has none (ESPN only has
open and close lines from about 2025), it's the book's last line, since the
odds are fetched after the game. Lines a source doesn't have are NULL.

```sql
-- how often the closing favorite covered
SELECT count(*) FILTER (WHERE (g.plus_minus + b.close_spread > 0) = (b.close_spread < 0)) / count(*)
FROM betting_lines b JOIN team_game_logs g
    ON g.season = b.season AND g.game_id = b.game_id AND g.team_id = b.home_team_id
WHERE b.season = 2027 AND b.provider_id = '100' AND b.close_spread <> 0 AND g.plus_minus + b.close_spread <> 0;
```

### `espn_injuries/season=<season>/data.parquet`

ESPN's NBA injury list
([site API](https://site.api.espn.com/apis/site/v2/sports/basketball/nba/injuries)),
as of every time it was fetched: one row per fetch and listed player. ESPN
only publishes the current list, so the history is what we saved: every
`update.yml` run (every 4 hours, plus 06:13 and 10:13 UTC) from November
12, 2026 (season 2027) on, with nothing earlier. Each fetch is kept at
`nba/raw/espn/<season>/injuries/<fetched_at>.json.gz`. Built by
`pipeline/espn_injuries.py`.

It's ESPN's reporting, not the league's official injury report, and it's
known before a game, so it's what a prediction of who plays can use;
`player_game_status` is what happened. In the first 13 games (November
12-13, 2026), 80 of 81 players ESPN listed `out` didn't play, 8 of 10
`day_to_day` did, and of the rostered players ESPN didn't list who sat
as inactive, 32 of 38 were on two-way contracts (`rosters_daily.two_way`). For a game, use the last fetch
before tip-off. A player who isn't listed in a fetch wasn't on ESPN's list
then, which is not the same as healthy if that fetch is missing.

ESPN's players are matched to NBA ids by name: on that day's saved team
rosters (`rosters_daily`'s source), on the player's team, else by a name
only one player in that season's `player_seasons` has (a player traded
since). Players whose names don't match are in `pipeline/player_ids.csv`
(source `espn`); a player that matches neither is left out and reported.

| Column | Type | Description |
|--------|------|-------------|
| season, team_id, player_id | | Key: `(fetched_at, player_id)`. `team_id` is ESPN's team for the player |
| fetched_at | TIMESTAMPTZ | When the list was fetched (the response's timestamp) |
| as_of_date | DATE | `fetched_at`'s US Eastern date |
| status | VARCHAR | ESPN's `INJURY_STATUS_*`, lowercased: `out`, `day_to_day`, `suspension`. ESPN's `out` can lag its news: a player still listed `out` with a `GTD` `fantasy_status` may play |
| fantasy_status | VARCHAR | ESPN's fantasy designation: `OUT`, `GTD` (game-time decision), `OFS` (out for season). Of the first 13 games' 81 `out` players, the one who played was `GTD` here |
| injury_type, location, side, detail | VARCHAR | The injury: body part (`Toe`, `Knee`, `Illness`), region (`Leg`), `Left`/`Right`, and what it is (`Sprain`, `Fracture`, `Soreness`). Null where ESPN has none |
| return_date | DATE | ESPN's expected return date |
| updated_at | TIMESTAMPTZ | When ESPN last updated the player's entry |
| short_comment, long_comment | VARCHAR | ESPN's news blurb about the injury |
| espn_athlete_id, espn_injury_id | VARCHAR | ESPN's ids for the player and the entry |

```sql
-- each team's injured players in the latest list
SELECT t.nba_abbrev, p.name, i.status, i.injury_type, i.detail, i.return_date
FROM espn_injuries i
JOIN players p USING (player_id)
JOIN team_seasons t USING (season, team_id)
WHERE i.season = 2027
  AND i.fetched_at = (SELECT max(fetched_at) FROM espn_injuries WHERE season = 2027)
ORDER BY 1, 2;
```

## v2 basketball-reference Data (`nba/bbref/`)

Built by `pipeline/bbref.py` from
[basketball-reference.com](https://www.basketball-reference.com/), seasons
2010 on. Raw pages are kept at `nba/raw/bbref/<season>/<page>.html.gz` (and
player pages at `nba/raw/bbref/players/<bbref_id>.html.gz`).
basketball-reference blocks fast scrapers, so pages are fetched at least 6
seconds apart, past seasons only once.

### `bbref_team_stats/season=<season>/data.parquet`

One row per team per season (regular season), from the five team tables on
the season's league page (`NBA_<season>.html`): totals, opponent totals,
advanced, shooting and opponent shooting. Column names are bbref's
`data-stat` names, except that counting stats use the NBA's names, as in
every other table: `fgm`, `fg3m`, `fg2m`, `ftm`, `oreb`, `dreb`, `reb`,
`min` (bbref's `fg`, `fg3`, `fg2`, `ft`, `orb`, `drb`, `trb`, `mp`).
Opponent columns start with `opp_`.

| Column | Type | Description |
|--------|------|-------------|
| season, team_id | | Key |
| made_playoffs | BOOLEAN | bbref marks playoff teams with `*` |
| g, min, fgm, fga, ..., pts | INTEGER (`min` DOUBLE) | Season totals; `min` is team minutes (5 x game minutes) |
| opp_fgm, ..., opp_pts | INTEGER | Opponents' totals |
| wins, losses, wins_pyth, losses_pyth | INTEGER | Record and Pythagorean record |
| mov, sos, srs | DOUBLE | Margin of victory, strength of schedule, simple rating system |
| off_rtg, def_rtg, net_rtg, pace | DOUBLE | Per 100 possessions; pace is possessions per 48 minutes |
| ts_pct, efg_pct, ft_rate, fta_per_fga_pct, fg3a_per_fga_pct, opp_efg_pct, opp_ft_rate | DOUBLE | Fractions (0.561) |
| tov_pct, orb_pct, opp_tov_pct, drb_pct | DOUBLE | **Percentages** (11.2), as bbref shows them |
| arena_name | VARCHAR | |
| attendance, attendance_per_g | INTEGER | |
| avg_dist, pct_fga_00_03, ..., fg_pct_fg3a | DOUBLE | Shot distance and shooting by distance |
| pct_ast_fg2, pct_ast_fg3, pct_fga_dunk, fg_dunk, pct_fga_layup, fg_layup, pct_fg3a_corner, fg3_pct_corner, fg3a_heave, fg3_heave | | Assisted shots, dunks, layups, corner 3s, heaves (the counts are INTEGER) |
| opp_avg_dist, ... | DOUBLE | The same shooting columns for opponents |

Per game is `total / g`. Per 100 possessions is `total / poss * 100` with
`poss = pace * min / 240`; that reproduces bbref's per-100 table within
0.1, since bbref also rounds pace. Totals agree with the NBA's game logs
(509 of 510 team-seasons exactly on games, points, field goals, assists and
wins); rebounds and turnovers differ slightly because the NBA and bbref
count team rebounds and team turnovers differently.

### `bbref_salaries/season=<season>/data.parquet`

One row per player per team per season, from the Salaries table on each
team's season page (`/teams/<abbrev>/<season>.html`, kept at
`nba/raw/bbref/<season>/teams/<abbrev>.html.gz`), built by
`pipeline/bbref_salaries.py`. Every row bbref lists is kept, so a team's
salaries add up to its payroll, including players it waived and still
pays. The exception: the rare player bbref has no page for (a draft pick
who never played, say) has no `bbref_id` and is left out.

| Column | Type | Description |
|--------|------|-------------|
| season, team_id, bbref_id | | Key. `bbref_id` is basketball-reference's player id (`tatumja01`) |
| player_id | VARCHAR | NBA id; NULL for players not in that season's `player_seasons` (mostly waived players who never played for anyone that season) |
| salary | INTEGER | Dollars that season, summed if bbref lists the player more than once for the team. NULL for two-way contracts, which bbref lists without a salary |

A player traded mid-season appears only under his last team. A player who
was waived or bought out appears under both teams: the old team's
remaining (or stretched) salary and the new team's contract, as with
Lillard in 2026 (MIL $22.5M, POR $14.1M). Both are real payroll, so team
sums are right; a player's sum is what he was paid that season. A player
bbref lists more than once for one team (consecutive 10-day contracts,
waived and re-signed, a buyout's split salary) has one row with the sum,
as with Isaac in 2027 (ORL $8M + $2.4M).

## v2 dunksandthrees Data (`nba/dunksandthrees/`)

Built by `pipeline/dunksandthrees.py` from the public season EPM tables at
[dunksandthrees.com/epm/actual](https://dunksandthrees.com/epm/actual)
(regular season, and `?seasontype=4` for the playoffs). Only the site's
current season is public, so there is no backfill: the data starts with
2026, and a season's file keeps the values from the last day the site
showed that season. EPM is recomputed daily, so the current season's file is
a snapshot; `metadata.updated` says when it was fetched. `epm_daily` and
`epm_predictive_daily` keep every day's values for the current season;
`team_epm` and `team_epm_daily` are the site's team ratings. Raw
pages are kept at `nba/raw/dunksandthrees/<season>/epm_<season_type>.html.gz`
(the latest) and `epm_<season_type>/<date>.html.gz` (every day, current
season only).

### `epm/season=<season>/data.parquet`

One row per player per season type, for players who played (the site also
lists rostered players with no games, which are dropped). Join `players` for
names and `team_seasons` for abbreviations.

| Column | Type | Description |
|--------|------|-------------|
| season, season_type, player_id | | Key; `season_type` is `regular_season` or `playoffs` |
| team_id | VARCHAR | The player's latest team that season |
| age, rookie_year | INTEGER | |
| position | VARCHAR | `PG`, `SG`, `SF`, `PF`, `C` |
| height_inches, weight | INTEGER | |
| gp, gs | INTEGER | Games played and started |
| roster_games | INTEGER | Games the player was on a roster for |
| min, min_per_game | DOUBLE | |
| o_epm, d_epm, epm | DOUBLE | Offensive, defensive and total EPM, points per 100 possessions. NULL for players with too few minutes |
| ewins | DOUBLE | Estimated wins added |
| usg_pct, ts_pct, efg_pct, fg_pct_rim, fg_pct_mid, fg2_pct, fg3_pct, ft_pct | DOUBLE | Fractions (0.561) |
| oreb_pct, dreb_pct, ast_pct, tov_pct, stl_pct, blk_pct | DOUBLE | Fractions |
| fga_rim_per_75, fga_mid_per_75, fg3a_per_75, fta_per_75, fga_per_75 | DOUBLE | Attempts per 75 possessions |

Not kept: names and abbreviations (use the lookup tables), and the site's
z-scores, ranks and percentiles for each stat (`*_attr`), which are a query
away.

### `epm_predictive/season=<season>/data.parquet`

The site's predictive EPM, from
[dunksandthrees.com/epm](https://dunksandthrees.com/epm): one row per
player, its prediction as of `as_of_date`. It is recomputed daily and the
file holds the latest prediction; every day's raw page is kept at
`nba/raw/dunksandthrees/<season>/epm_predictive/<date>.html.gz`. Players
in that season's `player_seasons` are kept, which includes injured players
on a roster who haven't played; the few who left a team without playing
are dropped. Every stat is a prediction.

| Column | Type | Description |
|--------|------|-------------|
| season, player_id | | Key |
| as_of_date | DATE | The date of the prediction |
| team_id | VARCHAR | |
| age, rookie_year, height_inches, weight | INTEGER | |
| position | VARCHAR | `G`, `F`, `C`, `F-C`, ... |
| o_epm, d_epm, epm | DOUBLE | Predicted offensive, defensive and total EPM, points per 100 possessions |
| epm_change | DOUBLE | Change in `epm` from the previous prediction (NULL so far) |
| start_pct | DOUBLE | Predicted fraction of games started |
| min_per_48, poss_per_48 | DOUBLE | Predicted minutes and possessions per 48 minutes |
| usg_pct, ts_pct, efg_pct, fg_pct_rim, fg_pct_mid, fg2_pct, fg3_pct, ft_pct | DOUBLE | Fractions |
| pts_per_100, fga_rim_per_100, fga_mid_per_100, fg2a_per_100, fg3a_per_100, fta_per_100, ast_per_100, tov_per_100, oreb_per_100, dreb_per_100, stl_per_100, blk_per_100 | DOUBLE | Per 100 possessions |

Not kept: names, abbreviations, the last game date (the same as
`as_of_date`), and the site's ranks and z-scores (`*_rk`, `*_z`).

### `epm_daily/season=<season>/data.parquet`

`epm` as of every day it was fetched, from 2027 (the first season fetched
daily): the same columns plus `as_of_date`, keyed by `as_of_date`,
`season_type` and `player_id`. The page has no date of its own, so
`as_of_date` is the day it was fetched (US Eastern, in the morning, so
through the previous night's games). Kept for the current season only; a
day the fetch failed is missing.

### `epm_predictive_daily/season=<season>/data.parquet`

`epm_predictive` for every day fetched, from 2027 (October 20, 2026, the
first saved page of 2027): the same columns, keyed by `as_of_date` and
`player_id`. A day the fetch failed is missing. Players are kept if they're
in the season's `player_seasons` as of the build.

```sql
-- a player's predictive EPM through the season
SELECT d.as_of_date, round(d.epm, 2) AS epm, round(d.o_epm, 2) AS o_epm,
  round(d.d_epm, 2) AS d_epm
FROM epm_predictive_daily d JOIN players p USING (player_id)
WHERE d.season = 2027 AND p.name = 'Jayson Tatum'
ORDER BY d.as_of_date;
```

### `team_epm/season=<season>/data.parquet`

The site's team ratings, from
[dunksandthrees.com/ratings](https://dunksandthrees.com/ratings): one row
per team as of `as_of_date`. A rating is the team's players' EPM weighted
by their expected minutes per game over the rest of the season (the site's
"Typical Rotation"; expected missed games from known injuries lower a
player's minutes), so it's predictive, not a record of games played.
Ratings are relative to a season average, so a day's ratings needn't
average 0. Recomputed daily; the file holds the latest day, and every
day's raw page is kept at
`nba/raw/dunksandthrees/<season>/epm_team_ratings/<date>.html.gz`. Starts with
2027: only today's ratings are free (other dates, past seasons and the
site's "Next Game" ratings are for subscribers), so there's no backfill.

| Column | Type | Description |
|--------|------|-------------|
| season, team_id | | Key |
| as_of_date | DATE | The date of the ratings |
| is_projection | BOOLEAN | Whether the site marks the ratings as a projection (false on every page so far) |
| o_epm, d_epm, epm | DOUBLE | Offensive, defensive and net rating, points per 100 possessions; `epm = o_epm + d_epm` |
| epm_change_10g | DOUBLE | Change in `epm` over the team's last 10 games; until the season's first game, its last 10 of last season, so it includes the offseason |
| o_sos, d_sos, sos | DOUBLE | Strength of schedule so far: the EPM of the opponents' players weighted by the possessions they actually played. Higher is tougher; `sos = o_sos + d_sos` |
| sos_games | INTEGER | Games behind the strength of schedule |

Not kept: names, records, ranks and z-scores, the next game, the trend's
line, the players behind each rating with their expected minutes, and
`team_*_season` ratings, which the page doesn't show or explain.

### `team_epm_daily/season=<season>/data.parquet`

`team_epm` for every day fetched, from 2027 (November 12, 2026, the first
saved page): the same columns, keyed by `as_of_date` and `team_id`. A day
the fetch failed is missing.

```sql
-- a team's rating through the season
SELECT d.as_of_date, round(d.epm, 1) AS epm, round(d.o_epm, 1) AS o_epm,
  round(d.d_epm, 1) AS d_epm
FROM team_epm_daily d JOIN team_seasons t USING (season, team_id)
WHERE d.season = 2027 AND t.nba_abbrev = 'BOS'
ORDER BY d.as_of_date;
```

## v2 OpenRAPM Data (`nba/openrapm/`)

Built by `pipeline/openrapm.py` from [OpenRAPM](https://openrapm.com)'s
published data, `docs/data/ratings.json` and `decompose_openrapm.json` in
[bbstats/openrapm](https://github.com/bbstats/openrapm) (MIT licensed).
OpenRAPM is RAPM (a ridge regression of the points scored on the ten
players on the court) pulled toward a box-score prior, fitted on regular
season and playoff games together. Its README explains the model.

Each publish recomputes every season, so every season's file is rewritten
when OpenRAPM's `built` date changes, and all of them hold the same version.
The raw files of each version are kept at
`nba/raw/openrapm/<built>/<name>.json.gz`. OpenRAPM rates seasons from
1997, but only seasons covered by `player_seasons` (2010 on) are kept.

### `openrapm/season=<season>/data.parquet`

One row per player per season, for players with possessions. Join
`players` for names.

| Column | Type | Description |
|--------|------|-------------|
| season, player_id | | Key |
| built | DATE | The date OpenRAPM built this version of the ratings |
| possessions | INTEGER | The player's offensive possessions on the court (OpenRAPM's `poss_season`) |
| o_rating, d_rating, rating | DOUBLE | Offensive, defensive and total rating, points per 100 possessions, positive is good. Two decimals, as published |
| wosa | DOUBLE | Wins over starter average: the regular-season wins the player added to his team over an average starter (the mean of the season's 150 players with the most starts), weighting each possession by its leverage in the game. Read from the regular season's ratings alone, so it changes through the current season and is fixed once the regular season ends. OpenRAPM's README explains it. Published from 2026-11-03; NULL in a version built before then |
| o_box_score, d_box_score | DOUBLE | The part of the rating from the box-score prior, less `box_adj` |
| o_on_court, d_on_court | DOUBLE | The part from the season's possessions the player was on the court for |
| o_off_court, d_off_court | DOUBLE | The part from the player's team's possessions without them |
| o_team_sos, d_team_sos | DOUBLE | The part from every other possession |
| o_box_adj, d_box_adj | DOUBLE | The part of the box-score prior learned from lineup swaps, which only moves credit between teammates (OpenRAPM's Box Adj). Split out of `box_score` from the version built 2026-11-03; it replaced `o_swap` and `d_swap`, which were 0 for every row |

The five pieces of each side add up to its rating, within 0.06 because
each piece is rounded to two decimals. They come from the decomposition
file, which is an extra page on the site; if it's missing or is for a
different version of the ratings, the pieces are NULL.

Not kept: names, and the decomposition's team abbreviations (teams are in
`player_game_logs`).

### `team_openrapm/season=<season>/data.parquet`

OpenRAPM's [Power Ratings](https://openrapm.com/power.html), built by
`pipeline/openrapm_power.py` from `docs/data/power.json` in its repo: one
row per team as of `through_date`. A team's rating is its players'
OpenRAPM weighted by the share of possessions each is expected to play
(a forecast), plus a correction from its recent games, "Last 10
Performance Over Expected". So, unlike `team_epm`, it's partly
results-based: `rating - recent` is the players' part alone. The 30
teams' ratings average 0 each day, so they need no centering.
Recomputed daily; the file holds the latest day. Current season only,
from 2027.

| Column | Type | Description |
|--------|------|-------------|
| season, team_id | | Key |
| through_date | DATE | The date of the last games counted |
| built | DATE | The date OpenRAPM built the file, usually the day after `through_date` |
| ready | BOOLEAN | Whether OpenRAPM marks the ratings as ready (every team has played enough games for the site to show them; 8, as of 2026-11-09). NULL if the file doesn't say |
| games | INTEGER | The team's games in the recent-games correction: its last 10, or fewer early in the season |
| o_rating, d_rating, rating | DOUBLE | Offensive, defensive and total rating, points per 100 possessions, positive is good. Two decimals, as published; `rating = o_rating + d_rating` within 0.01 |
| o_recent, d_recent, recent | DOUBLE | The recent-games correction included in the rating: how much better the team played in its last 10 games than its players' ratings expected |

Not kept: names, and each team's players with their expected shares of
possessions, which are in the raw files.

### `team_openrapm_daily/season=<season>/data.parquet`

`team_openrapm` for every day, keyed by `through_date` and `team_id`, from
games through 2026-11-08, the first day of OpenRAPM's current method (the
files before it had no recent-games correction and aren't kept). Every
day's file is in OpenRAPM's git history, so a day a run missed is filled in
by the next; a day OpenRAPM rebuilt keeps its newest build. Raw files are
at `nba/raw/openrapm/power/<season>/<through_date>.json.gz`.

```sql
-- a team's power rating through the season, with the players' part
SELECT d.through_date, d.rating, d.rating - d.recent AS players, d.recent
FROM team_openrapm_daily d JOIN team_seasons t USING (season, team_id)
WHERE d.season = 2027 AND t.nba_abbrev = 'SAS'
ORDER BY d.through_date;
```

## v2 College Basketball (`ncaam/`)

Men's college basketball, separate from the NBA data: its own prefix, and
its own catalog, `ncaam/ncaam.duckdb`, with a view per dataset (torvik's
`torvik_team_results`, `torvik_four_factors`, `torvik_ratings_daily`, and
ESPN's `games`, `team_box`, `player_box`, `team_seasons`,
`player_seasons`, `betting_lines`), and `players` and `metadata` tables like `nba.duckdb`'s:

```sql
ATTACH 'https://basketball-data.billmill.org/ncaam/ncaam.duckdb' AS ncaam;
SELECT * FROM ncaam.torvik_team_results WHERE season = 2026 ORDER BY barthag DESC;
```

The [layout](#layout), types, `snake_case` names, fractions and NULLs follow
the v2 conventions; seasons are end years (2026 = 2025-26). There are no
NBA ids:

- **ESPN's datasets** are keyed by ESPN's ids, as strings: `game_id`,
  `team_id` (and `opp_team_id`, `home_team_id`, `away_team_id`),
  `player_id`. `games`, `team_seasons` and `player_seasons` are this
  catalog's lookup tables, with the same names and the same
  [integrity](#v2-catalog-nbanbaduckdb) rule as the NBA's: every key is in
  them for the row's season
- **torvik's datasets** are keyed by **torvik's team name** (`team`), which
  torvik applies to every season (a renamed school has its current name
  throughout), and which is the same in every torvik dataset (the daily
  ratings' older names are mapped to it)
- **Joining them:** `team_seasons.torvik_team` is the team's torvik name
  (from `pipeline/ncaam_teams.csv`), so ESPN's games join to torvik's
  ratings:

```sql
-- UConn's 2026 games, with torvik's rating the day before each
SELECT b.game_date, o.display_name AS opponent, b.pts, b.opp_pts, d.barthag
FROM ncaam.team_box b
JOIN ncaam.team_seasons t USING (season, team_id)
JOIN ncaam.team_seasons o ON o.season = b.season AND o.team_id = b.opp_team_id
LEFT JOIN ncaam.torvik_ratings_daily d
    ON d.season = b.season AND d.team = t.torvik_team AND d.date = b.game_date - 1
WHERE b.season = 2026 AND t.torvik_team = 'Connecticut'
ORDER BY b.game_date;
```

| blk_pct, opp_blk_pct | DOUBLE | Block rate: the team's blocks, and the share of its shots blocked. **Inferred:** these columns have no header in the CSV. The first tracks opponents' 2P% (r = -0.56) and not forced turnovers (0.09), so it's blocks rather than steals |

nba0bservable's four factors page reads the 2026 CSV directly; from here
that's `torvik_four_factors WHERE season = 2026`, times 100 for its
percentages.

#### `torvik_ratings_daily/season=<season>/data.parquet`

The T-Rank ratings as torvik published them after each day's games, from
its "time machine", seasons 2010 on: one row per team per day, with the
columns of `torvik_team_results` (and the same NULLs), except `date` in
place of `as_of_date`.

```sql
SELECT date, wins, losses, adj_oe, adj_de, barthag
FROM ncaam.torvik_ratings_daily
WHERE season = 2026 AND team = 'Connecticut' ORDER BY date;
```

| Column | Type | Description |
|--------|------|-------------|
| season, date, team | | Key. The ratings after `date`'s games (the snapshot dated the night of the title game includes it) |
| ... | | Every column of `torvik_team_results` but `as_of_date` |

- **Coverage:** every day from the first snapshot to the title game:
  January 31 on for 2010-2014, early or mid-November for 2015-2020 (2020
  ends March 30, after the season was cancelled), and November 1, with
  the preseason projections before the first game, from 2021. 2024 and
  2025 also run to April 15 with copies of the final ratings. The current
  season gets each
  day's snapshot the day after (torvik publishes them the next afternoon).
  There are no gaps within a season but one: torvik's file for 2013-03-17
  is corrupt
- **As published:** these are the ratings torvik showed that day. Torvik
  has since recomputed past seasons, so for 2010-2019 the last day differs
  from `torvik_team_results` by about 1 point of adjusted efficiency (barthag
  correlates at 0.9997+); from 2020 they match. The 2017-2019 snapshots'
  records leave out games against non-Division I teams, which the season
  CSVs count (Michigan 2018: 32-8 here, 33-8 there)
- **Names:** torvik's snapshots use the names of their time ("North
  Carolina St."). They're mapped to the current names that the other two
  datasets use (`N.C. State`), from `pipeline/torvik_names.csv`, so `team`
  joins across datasets and seasons. Every team joins to that season's
  `torvik_team_results` except ten that didn't play in 2021 (the Ivy
  League, Bethune-Cookman, Maryland Eastern Shore), which torvik projected
  in the preseason
- **Not kept:** after the title game in 2020-2023, torvik's snapshots are
  the next season's preseason projections (no games played); those days
  are dropped

Raw snapshots are kept as served, at
`ncaam/raw/torvik/<season>/daily/<date>.json.gz`; `missing.txt` there lists
the days torvik has no snapshot for (`404`) or a corrupt one (`corrupt`),
which are never requested again.

### ESPN (`ncaam/espn/`)

Built by `pipeline/ncaam_espn.py` from ESPN's game data, seasons 2005 on:
every finished game involving a Division I team, including games against
lower-division opponents, and the postseason (conference tournaments are
`regular_season`, as ESPN has them; the NCAA tournament, NIT and other
national tournaments are `postseason`). About 4,300-6,300 games a season.

- **2005-2026** come from [sportsdataverse](https://github.com/sportsdataverse/sportsdataverse-data)'s
  hoopR files (MIT license), ESPN's data already scraped and published as
  parquet, kept as downloaded at
  `ncaam/raw/espn/<season>/sportsdataverse/<schedule|team_box|player_box>.parquet`.
  Their schedules list about 1,500 finished games with no box score; those
  were fetched from ESPN, which had box scores for 156 of them (35 are
  Eastern Washington's 2017 season)
- **The current season** comes from ESPN directly, daily: a scoreboard of
  every Division I game per day, and each finished game's summary, kept
  at `ncaam/raw/espn/<season>/scoreboard/<date>.json.gz` and
  `.../summary/<game_id>.json.gz`. Summaries keep the header, box score,
  game info, play-by-play, win probability and (from November 2026)
  betting lines (`pickcenter`), without ESPN's news and videos. ESPN's and sportsdataverse's data agree
  exactly where they overlap (checked on 2026 games, every column)
- **Box score gaps:** a game in `games` can be missing from `team_box`
  and `player_box`, where ESPN has no box score: 681 games in 2005, about
  240 a season in 2006-2007, 31-77 in 2008-2009, and 0-10 a season
  since. 35 games (most in 2010-2013 and 2025) have player box scores but
  no team box. In 2005-2013, players' points sum to the team's in 97-99.7%
  of team games; since 2014, in about 99.9% (players missing from ESPN's
  box score)
- **Players with no id:** ESPN has lost the athlete record for a few
  players (one on Eastern Washington in 2017), whose stat lines have no
  id or name. They're left out of `player_box`, so their team's players
  don't add up to its box score in those games

## NBA Game ID Format

Game IDs follow this pattern: `00X YY ZZ GGGG`

| Prefix | Game Type |
|--------|-----------|
| 001 | Preseason |
| 002 | Regular Season |
| 003 | All-Star |
| 004 | Playoffs |
| 005 | Play-In Tournament |
| 006 | NBA Cup Final |

- `YY` = Season year (24 = 2024-25)
- `ZZ` + `GGGG` = Game-specific identifier

For playoff and play-in games, the last three digits encode the bracket:

```
004 YY 00 R S G    playoffs:  R = round (1-4), S = series within the round,
                              numbered from 0, G = game within the series (1-7)
005 YY 00 R S 1    play-in:   R = round (1-2), S = game within the round,
                              numbered from 0
```

So `0042500407` is game 7 of the 2025-26 Finals, and `0052500211` is the
second game of the 2025-26 play-in's second round. Verified against the
2025-26 postseason: round 1 has series 0-7, round 2 has 0-3, round 3 has
0-1, and the Finals 0.

In v2, these fields are decoded once into the `games` table (`game_type`,
`playoff_round`, `series_number`, `series_game`); other tables join `games` on
`game_id` rather than parsing the id.
