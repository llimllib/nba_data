# nba_data v2

The plan for moving nba_data out of git and into object storage, as a single
dataset with consistent keys. Work is tracked in the GitHub milestone
[v2: object storage & a coherent dataset](https://github.com/llimllib/nba_data/milestones);
this document records the decisions behind it and how the transition works.
Update it when a decision changes.

## Why

The update workflow commits fresh data every 4 hours. Parquet doesn't
delta-compress, so every commit stores full copies of the changed files, and
the repo grew past 6GB (`espn/player_details.parquet` alone is 3.8GB of
history). Separately, the datasets use inconsistent keys, names and types, so
joining them takes ad hoc matching on team abbreviations.

## Decisions

- **Hosting:** the DigitalOcean Space `basketball-data` (sfo3, CDN enabled).
  Not `nba-data`, which nba0bservable's publish workflow syncs with
  `--delete`. Setup is recorded in
  [#38](https://github.com/llimllib/nba_data/issues/38).
- **Scraping:** keep GitHub Actions with the Tailscale exit node, which is
  needed because nba.com blocks Azure IPs.
- **Storage:** one parquet file per dataset per season. Finished seasons are
  never rewritten; each run rewrites only the current season. Raw source
  responses are kept, gzipped.
- **Catalog:** `nba/nba.duckdb` contains only views over the parquet URLs,
  plus a metadata table. `ATTACH` it to get every table by name. Not a single
  database file holding the data, which would be re-uploaded whole every run.
- **Schema:** NBA ids are the keys everywhere, as strings; seasons are end
  years; team names come from `team_seasons`. See "v2 Schema Conventions" in
  [DATA_DICTIONARY.md](DATA_DICTIONARY.md).
- **Lookup tables** (`team_seasons`, `player_seasons`, `games`) are built per
  season from the NBA responses, like every other dataset, so a run only
  touches the current season. The catalog unions them and derives `players`
  (each player's latest name). Neutral-site games have `neutral_site` set and
  no home or away team.
- **Upload:** the AWS CLI (`aws s3 sync`), as in nba0bservable. The Python
  code only reads and writes a local directory laid out like the bucket.
- **Tools:** Python, with DuckDB for transforms rather than pandas.
- **NBA fetching:** refetch the whole current season every run (14 requests:
  game logs and season stats in bulk, not per-game box scores), so the NBA's
  stat corrections are picked up. Season stats are stored as totals; per-game,
  per-36 and per-100 values are computed, which reproduces the NBA's values
  (verified against v1; see [#42](https://github.com/llimllib/nba_data/issues/42)).

## Transition

- **v1 is frozen.** `src/`, `data/` and the `dl.yml` and `gh-pages.yml`
  workflows keep running unchanged until cutover
  ([#50](https://github.com/llimllib/nba_data/issues/50)). Only fix bugs that
  break them.
- **v2 code lives in `pipeline/`**, tests in `tests/pipeline/`. v2 never
  imports from `src/`; helpers it needs (e.g. the nba_api wrappers in
  `src/stats.py`) are copied over and adapted. Cutover deletes `src/` without
  breaking anything.
- **Local runs write to `out/`** (gitignored), laid out like the bucket. Sync
  it up by hand when needed:
  `aws s3 sync out/ s3://basketball-data/ --acl public-read --profile do`
- **Work happens on `main`.** The cron commits data to `main` every 4 hours,
  so a long-lived branch would need constant rebasing, and v2 code can't
  affect v1.
- **Dual-writing starts with the new workflow**
  ([#47](https://github.com/llimllib/nba_data/issues/47)): v1 writes to git,
  v2 writes to the bucket, with no shared files. Before that, v2 only runs
  locally.
- **After cutover**, `data/` is stripped from git history
  ([#51](https://github.com/llimllib/nba_data/issues/51)).

## Bucket layout

```
nba/raw/<source>/<season>/...            raw responses, gzipped
nba/<source>/<dataset>/<season>.parquet  one file per season
                                         (sources: stats = stats.nba.com, espn)
nba/nba.duckdb                           catalog of views
```

## Open questions

- The NBA backfill should refetch rather than convert v1's files: a season
  is only 14 requests, and v1's NBA data has stale values (no stat
  corrections), gaps (postseason game logs before 2026, player stats before
  2014) and dropped players
  ([#46](https://github.com/llimllib/nba_data/issues/46))
- ESPN's past days can change and lose data (2025-11-05 now lacks one game's
  team box), so the backfill converts v1's saved ESPN files instead of
  refetching them. v1 also missed the 2020 bubble (ESPN data stops
  2020-03-11), which does need fetching
  ([#46](https://github.com/llimllib/nba_data/issues/46))
