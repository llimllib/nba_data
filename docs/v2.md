# nba_data v2

The plan for moving nba_data out of git and into object storage, as a single
dataset with consistent keys. Work is tracked in the GitHub milestone
[v2: object storage & a coherent dataset](https://github.com/llimllib/nba_data/milestones);
this document records the decisions behind it and how the transition works.
Update it when a decision changes.

## Why

The update workflow commits fresh data every 4 hours. Parquet doesn't
delta-compress, so every commit stores full copies of the changed files, and
the repo grew past 6GB (`espn/player_details.parquet` alone is 3.8GB of
history). Separately, the datasets use inconsistent keys, names and types, so
joining them takes ad hoc matching on team abbreviations.

## Decisions

- **Hosting:** the DigitalOcean Space `basketball-data` (sfo3, CDN enabled).
  Not `nba-data`, which nba0bservable's publish workflow syncs with
  `--delete`. Setup is recorded in
  [#38](https://github.com/llimllib/nba_data/issues/38). Served at
  `https://basketball-data.billmill.org`, a custom subdomain on the CDN
  ([#54](https://github.com/llimllib/nba_data/issues/54)), so the data can
  move hosts without breaking URLs. The catalog's views use this URL.
- **Scraping:** keep GitHub Actions with the Tailscale exit node, which is
  needed because nba.com and barttorvik.com block Azure IPs (torvik returns
  403; [#73](https://github.com/llimllib/nba_data/issues/73)). Only those
  two go through it; the other sources fetch directly.
- **Storage:** one parquet file per dataset per season, at
  `<dataset>/season=<season>/data.parquet` so that DuckDB's hive
  partitioning skips the files a season filter doesn't need. The catalog's
  views only use `union_by_name` for a dataset whose seasons' columns
  differ, since it makes DuckDB open every file
  ([#55](https://github.com/llimllib/nba_data/issues/55)). Finished seasons are
  never rewritten; each run rewrites only the current season. Raw source
  responses are kept, gzipped.
- **Catalog:** `nba/nba.duckdb` contains views over the parquet URLs, plus
  `metadata` and `players`, which are small tables. `ATTACH` it to get every
  table by name. Not a single database file holding the data, which would be
  re-uploaded whole every run. `players` is the exception because it covers
  every season: as a view, every query that joined it would open every file
  ([#56](https://github.com/llimllib/nba_data/issues/56)). For DuckDB 1.1.1
  (Observable Framework's DuckDB-wasm), no view reads another view
  ([#57](https://github.com/llimllib/nba_data/issues/57)) and the file is
  written with storage version v1.0.0
  ([#58](https://github.com/llimllib/nba_data/issues/58)).
  The views list their files from the bucket and read them through the CDN.
  DuckDB reads a view's files when it creates the view, so a run uploads the
  parquet files first, then builds the catalog and uploads it
  ([#44](https://github.com/llimllib/nba_data/issues/44)).
  The `metadata` table is also uploaded as `nba/metadata.json`, so clients
  that read the parquet without DuckDB (the site, with hyparquet) can find
  each dataset's seasons. It's read back from the table, so the two can't
  disagree, and like the catalog it's a published interface
  ([#85](https://github.com/llimllib/nba_data/issues/85)).
- **Schema:** NBA ids are the keys everywhere, as strings; seasons are end
  years; team names come from `team_seasons`. See "v2 Schema Conventions" in
  [DATA_DICTIONARY.md](DATA_DICTIONARY.md).
- **Lookup tables** (`team_seasons`, `player_seasons`, `games`) are built per
  season from the NBA responses, like every other dataset, so a run only
  touches the current season. The catalog unions them and derives `players`
  (each player's latest name). Neutral-site games have `neutral_site` set and
  no home or away team.
- **Upload:** the AWS CLI (`aws s3 sync`), as in nba0bservable. The Python
  code only reads and writes a local directory laid out like the bucket.
- **Caching:** files are uploaded with `Cache-Control: public, max-age=0,
  must-revalidate, s-maxage=3600`: the CDN caches them for an hour (and is
  purged after each upload), and browsers revalidate on every load, which
  costs a 304. With the CDN's default `max-age=3600`, Firefox combined
  cached ranges of a rewritten file with ranges of the new one, and the
  site's parquet reader failed on an invalid footer. `no-cache` would also
  fix that, but the CDN then doesn't cache the file at all.
- **Tools:** Python, with DuckDB for transforms rather than pandas.
- **NBA fetching:** refetch the whole current season every run (14 requests:
  game logs and season stats in bulk, not per-game box scores), so the NBA's
  stat corrections are picked up. Season stats are stored as totals; per-game,
  per-36 and per-100 values are computed, which reproduces the NBA's values
  (verified against v1; see [#42](https://github.com/llimllib/nba_data/issues/42)).
  Team rosters (30 requests) add rostered players who haven't played to
  `player_seasons`, with `played = false`, so sources that list injured
  players (EPM) pass the integrity check. They're refetched once a day:
  `update.yml` downloads the saved ones and `pipeline.stats` refetches them
  when they're over 20 hours old ([#70](https://github.com/llimllib/nba_data/issues/70)).
  The saved file also keeps every player from earlier rosters that season
  (`former`), so a player waived before they play stays in `player_seasons`
  and the salary rows that refer to them stay valid.
- **Bad rows don't stop the update:** a row with a duplicate or NULL key
  is a source's mistake (the NBA and ESPN both once had Devin Booker on
  both teams in a game), and failing the run on it held back every
  dataset for a day. Known mistakes have a rule that resolves them (keep
  the row with the most minutes, or possessions). Anything else:
  `check_keys` raises locally, but in the workflows (`PIPELINE_DROPPED`)
  it drops every row with that key, the rest is published, and then the
  run fails and the failure issue lists the dropped rows. A missing row
  is less wrong than a guessed one, and it comes back when the source
  fixes it, since the current season is rebuilt every run.
- **Keep what's fetched:** a dataset built from a source keeps everything
  in it that's useful, not just what the first use needed, so a new use
  is a rebuild rather than a refetch. The play-by-play is published whole
  as `game_events`, every action with the score after it, rather than a
  table per use (it replaced `game_scoring`, which had only the scoring
  plays and left out fouls).

## Transition

- **v1 is frozen.** `src/`, `data/` and the `dl.yml` and `gh-pages.yml`
  workflows keep running unchanged until cutover
  ([#50](https://github.com/llimllib/nba_data/issues/50)). Only fix bugs that
  break them.
- **v2 code lives in `pipeline/`**, tests in `tests/pipeline/`. v2 never
  imports from `src/`; helpers it needs (e.g. the nba_api wrappers in
  `src/stats.py`) are copied over and adapted. Cutover deletes `src/` without
  breaking anything.
- **Local runs write to `out/`** (gitignored), laid out like the bucket. Sync
  it up by hand when needed:
  `aws s3 sync out/ s3://basketball-data/ --acl public-read --exclude nba.local.duckdb --profile do`
- **Work happens on `main`.** The cron commits data to `main` every 4 hours,
  so a long-lived branch would need constant rebasing, and v2 code can't
  affect v1.
- **Dual-writing** ([#47](https://github.com/llimllib/nba_data/issues/47)):
  v1 (`dl.yml`) writes to git, v2 (`update.yml`, 30 minutes later) writes to
  the bucket, with no shared files. `update.yml` fetches, runs the integrity
  check on the run's own files, uploads, purges the CDN, then builds the
  catalog from the bucket and uploads it. The other sources (bbref,
  dunksandthrees, OpenRAPM, Cleaning the Glass, ESPN's season net points, and
  barttorvik for college) run once a day in `sources.yml`, which shares `update.yml`'s concurrency group so
  the two never rebuild the catalog at the same time. Its integrity check
  reads the lookup tables from the bucket (`catalog --check
  --remote-lookups`), since its `out/` has only the sources' own files.
  Each source is its own step with `continue-on-error`: a source whose page changed
  writes nothing (its parser validates before writing), the others still
  publish, and the failure goes to a per-source issue titled
  "<source> scraper failed"
  ([#67](https://github.com/llimllib/nba_data/issues/67)).
- **After cutover**, `data/` is stripped from git history
  ([#51](https://github.com/llimllib/nba_data/issues/51)).

## Bucket layout

```
nba/raw/<source>/<season>/...                        raw responses, gzipped
nba/<source>/<dataset>/season=<season>/data.parquet  one file per season
                                                     (sources: stats = stats.nba.com, espn)
nba/nba.duckdb                                       the catalog
nba/metadata.json                                    its metadata table, as JSON
ncaam/raw/<source>/<season>/...                      college basketball, the same way
ncaam/<source>/<dataset>/season=<season>/data.parquet  (sources: torvik, espn)
ncaam/ncaam.duckdb                                   its own catalog
ncaam/metadata.json                                  its metadata table, as JSON
```

## Code

| Module | What it does |
|--------|--------------|
| `pipeline/stats.py` | stats.nba.com: 14 bulk requests per season, plus 30 team rosters once a day -> `nba/raw/stats/`, then `team_game_logs`, `player_game_logs`, `player_season_stats` and the lookups |
| `pipeline/rotations.py` | Each game's play-by-play and box score from stats.nba.com -> `nba/raw/stats/<season>/playbyplay/<game_id>.json.gz`, then `game_rotations` (player stints with points and plus-minus, for rotation charts), derived from the substitutions and the running score and checked against `player_game_logs`, and `game_events` (every play-by-play action with the score after it, for worm charts and anything else that needs the plays). Incremental: only new games and the last two days'. Daily in `sources.yml`, through the exit node |
| `pipeline/lookups.py` | `team_seasons`, `player_seasons`, `games`, built inside `stats.build_season` |
| `pipeline/espn.py` | ESPN daily files -> `nba/raw/espn/`, then `four_factors`, `player_box`, `team_box`, `player_details` |
| `pipeline/espn_net_pts.py` | ESPN's season net points totals (ESPN ids, matched to NBA ids by name) -> `net_pts_season`, daily in `sources.yml`. ESPN's own totals; for 2019-2025 they equal sums of `player_box` ([#66](https://github.com/llimllib/nba_data/issues/66), [#72](https://github.com/llimllib/nba_data/issues/72)) |
| `pipeline/teams.py`, `team_abbrevs.csv` | Abbreviation -> `team_id` for sources without team ids (ESPN, bbref) |
| `pipeline/bbref.py` | basketball-reference fetching (6s between requests, no retries, every page kept under `nba/raw/bbref/`) and parsing; builds `bbref_team_stats` from each season's league page ([#63](https://github.com/llimllib/nba_data/issues/63)) |
| `pipeline/bbref_salaries.py` | basketball-reference team season pages (30 a season, through `bbref.Fetcher`) -> `bbref_salaries`, keyed by `(team_id, bbref_id)` with a nullable `player_id`, so waived players still count toward payroll ([#53](https://github.com/llimllib/nba_data/issues/53)) |
| `pipeline/ctg.py` | Cleaning the Glass's public league summary page (regular season and playoffs): builds `ctg_team_summary` with the fetch date, since its last-two-weeks columns change daily; past seasons fetched once ([#64](https://github.com/llimllib/nba_data/issues/64)) |
| `pipeline/dunksandthrees.py` | dunksandthrees' public EPM: parses the javascript literal embedded in each page, and builds `epm` (season EPM, regular season and playoffs; [#65](https://github.com/llimllib/nba_data/issues/65)) and `epm_predictive` (the latest daily prediction; [#70](https://github.com/llimllib/nba_data/issues/70)) for whichever season the site is on |
| `pipeline/openrapm.py` | OpenRAPM's published ratings (`ratings.json` and `decompose_openrapm.json` from its GitHub repo) -> `openrapm`, a rating per player-season with its box-score and games' pieces, 2010 on. Each publish recomputes every season, so all of them are rewritten when its `built` date changes ([#86](https://github.com/llimllib/nba_data/issues/86)) |
| `pipeline/player_ids.py`, `player_ids.csv` | Source player id -> NBA `player_id` (bbref so far): matched by name, team and season, then the source's player page, then by hand ([#62](https://github.com/llimllib/nba_data/issues/62)) |
| `pipeline/torvik.py`, `torvik_names.csv` | barttorvik.com's season CSVs (2 a season, 2008 on) -> `ncaam/torvik/`: `torvik_team_results` and `torvik_four_factors`, keyed by torvik's team names ([#68](https://github.com/llimllib/nba_data/issues/68)). And its time machine's daily snapshots (2010 on, each fetched once) -> `torvik_ratings_daily`, with old team names mapped to current ones |
| `pipeline/ncaam_espn.py`, `ncaam_teams.csv` | College games and box scores -> `ncaam/espn/`: `games`, `team_box`, `player_box` and the college lookups `team_seasons` and `player_seasons`, keyed by ESPN ids. Past seasons from sportsdataverse's files, the current one from ESPN's scoreboard and summary API; `ncaam_teams.csv` maps ESPN team ids to torvik names ([#74](https://github.com/llimllib/nba_data/issues/74)) |
| `pipeline/catalog.py` | `nba/nba.duckdb`: lists the parquet files (in the bucket, or in `out/` for a local catalog at `out/nba.local.duckdb`) and writes views over them. With `--bucket`, also `nba/metadata.json`, the `metadata` table as JSON. `--league ncaam` does the same for `ncaam/ncaam.duckdb` |
| `pipeline/integrity.py` | Run by the catalog build: every `*team_id`, `*player_id` and `*game_id` must be in `team_seasons`, `player_seasons` or `games` for the same season ([#45](https://github.com/llimllib/nba_data/issues/45)). `pipeline.catalog --check` runs it alone on `out/`, before uploading |
| `pipeline/output.py` | Atomic parquet writes and key checks |
| `pipeline/seasons.py` | Current season, season date windows (including the covid seasons) |

Each pipeline only reads and writes a local directory laid out like the
bucket, and only rewrites the seasons it's asked for. The catalog build needs
to know every parquet file, though, and in CI only the current season is
present locally, so with `--bucket` it lists the bucket instead (credentials
and endpoint from the usual `AWS_*` environment variables).

- **Rotations come from the play-by-play, not `gamerotation`:** the NBA's
  stint endpoint takes ~30s a game when it works, returned a 500 for about
  40% of 2025-26 games and every playoff game tried (2015-2026), and
  nothing on nba.com uses it. `playbyplayv3` (what nba.com's game pages
  embed) answers in under a second for every season. Its subs only have the
  outgoing player's id, so the incoming one is matched by name, and it
  doesn't list who starts a period, so that's inferred (with a one-period
  box score when a player did nothing). On 40 games with both, the derived
  stints matched `gamerotation`'s except where `gamerotation` disagreed with
  the box score. The score is counted from made shots and free throws (the
  rows' own scores are sometimes wrong, and counting matches all 461 games'
  final scores). Across 440 games from 2010-2027, 437 add up to every
  player's plus-minus and minutes (one is ±1 around a technical, two have a
  broken play-by-play), and 2,777 of the 2,787 saved for 2025-2027, after
  learning from the full 2025 backfill that free throws shot by a player
  subbed in, and flopping technicals' free throws, count for the lineup
  after the subs (the 2025 All-Star games have no game clock, so no
  stints); the build flags the ones that don't in
  `matches_box_score`. `playbyplayv2` is retired and the CDN's live
  play-by-play is blocked by Akamai, even for a browser. Fetching two games
  at a time a second apart was rate limited after ~600 requests, so it's
  one at a time, and when half the last 20 games have failed it pauses
  (5, 10, then 20 minutes) before giving up; a run that gives up still
  writes what it got, then exits with an error

## Open questions

- The NBA backfill should refetch rather than convert v1's files: a season
  is only 14 requests, and v1's NBA data has stale values (no stat
  corrections), gaps (postseason game logs before 2026, player stats before
  2014) and dropped players
  ([#46](https://github.com/llimllib/nba_data/issues/46))
- ESPN's past days can change and lose data (2025-11-05 now lacks one game's
  team box), so the backfill converts v1's saved ESPN files instead of
  refetching them. v1 also missed the 2020 bubble (ESPN data stops
  2020-03-11), which does need fetching
  ([#46](https://github.com/llimllib/nba_data/issues/46)).
  Seasons 2022-2025 were later refetched after all
  ([#72](https://github.com/llimllib/nba_data/issues/72)): v1's copies
  predated ESPN's newer format (no possessions or WPA) and its
  recomputation. Fetched into a separate directory and compared first, the
  refetch lost no games or team rows, added 3 games v1 had missed (2024
  Finals games 3-5) and 310 player-games, and dropped 9 low-minute
  player-games that ESPN's own season totals no longer count either

## Later milestones

- **v2: browser-ready catalog** (#55-#61, done): nba0bservable found the
  catalog took 7-14s cold for one page query in DuckDB-wasm, because every
  view opened every season's file. Fixed with season-partitioned paths,
  `players` as a table, no view-to-view references (DuckDB 1.1.1 can't
  resolve them), a pinned storage version, and `team_seasons.is_nba`. The
  browser re-test (#61) brought the query to about 1.7s, 1.6x reading the
  files directly, but only with DuckDB-wasm 1.32+ using the httpfs extension
  (`SET builtin_httpfs = false; LOAD httpfs;`). DuckDB-wasm's built-in HTTP
  backend sends a HEAD to every file in a view's list before each query, and
  since 1.30 it can't detect range support
  ([duckdb/duckdb-wasm#2228](https://github.com/duckdb/duckdb-wasm/issues/2228)),
  so it downloads whole files. Build-time loaders don't need any of this:
  their output is cached, and they should keep only the columns pages use
  and round computed values
- **v2: in-browser catalog** (#52): load `nba.duckdb` in Observable with
  DuckDB-wasm 1.32+ and the httpfs workaround above, until #2228 is fixed.
  Note that `LOAD httpfs` fetches the extension from `extensions.duckdb.org`
  at runtime unless it's self-hosted
- **v2: more NBA sources** (#53, #62-#67): the data nba0bservable's loaders
  scrape, as v2 datasets: basketball-reference team and player stats and
  salaries, Cleaning the Glass's team summary, and dunksandthrees' EPM.
  Public data only (CTG and EPM have paid tiers, which stay out). None of
  them use NBA ids, so the first step is a shared `(source, source_id) ->
  player_id` table (#62), like `team_abbrevs.csv` for teams. They change at
  most daily and bbref rate-limits hard, so they run daily, and a failing
  source mustn't stop the others (#67). dunksandthrees only shows its
  current season publicly (others redirect to a subscribe page), so EPM
  starts with 2026 and can't be backfilled (#65). Cleaning the Glass's
  league summary is public for every season, so it's backfilled from 2010
  (#64)
- **OpenRAPM** (#86): [openrapm.com](https://openrapm.com)'s ratings,
  which are RAPM pulled toward a box-score prior, built from the same
  stats.nba.com play-by-play we fetch. Its site is static, and its data is
  JSON in its repo, already keyed by NBA ids. It's the exception to
  "finished seasons are never rewritten": each publish is a new model
  version that recomputes every season, so the table always holds one
  version, the latest, with its `built` date on every row. Old versions
  stay in openrapm's git history and in our raw files. It rates seasons
  from 1997, but our lookups start in 2010, so the earlier seasons wait
  for the stats.nba.com backfill
  ([#89](https://github.com/llimllib/nba_data/issues/89)). openrapm also
  uses stats.nba.com endpoints we don't fetch (hustle, tracking, Synergy
  play types, matchups), listed in
  [#88](https://github.com/llimllib/nba_data/issues/88)
- **College basketball** (#68, done): barttorvik.com's team results and four
  factors, 2008 on, under `ncaam/` (the bucket's `nba/` prefix left room
  for it). Its own catalog, `ncaam/ncaam.duckdb`, built by the same code
  (`catalog --league ncaam`): it shares no keys with the NBA data, keeps
  `nba.duckdb` small, and avoids name clashes (both have four factors).
  Teams are keyed by torvik's names, which torvik applies to every season
  and which match between its two files; a second college source would
  need an `ncaam` team lookup first. Torvik's URL years are season end
  years, like ours. Its HTML pages sit behind a JavaScript check and
  refuse headless browsers, but the CSVs don't, so the four factors' two
  unlabeled columns were identified from the data (block rates).
  `torvik_ratings_daily` keeps the ratings as published each day, from
  torvik's time machine (one gzipped JSON per day), so a season's history
  survives torvik recomputing it later. Backfilled from 2010 (about 2,500
  requests, 2 seconds apart); a run fetches only the days it doesn't have,
  and remembers torvik's 404s and corrupt files so they're never requested
  again. A run builds the season from every saved day, so `sources.yml`
  downloads the season's snapshots from the bucket first
- **College games and box scores** (#74): ESPN's, under `ncaam/espn/`.
  Past seasons (2005-2026) come from sportsdataverse's hoopR files, which
  are ESPN's data already scraped and published as parquet on GitHub, so
  the backfill cost ESPN about 1,500 requests: the finished games their
  files have no box score for (ESPN had 156). The current season comes
  from ESPN's public API, one scoreboard a day and one summary per
  finished game, a request a second; sportsdataverse's own daily job
  runs a day behind and fails at times. NCAA.com has similar JSON, but
  its ids match nothing else. The keys are ESPN's ids, and the college
  catalog's lookups (`games`, `team_seasons`, `player_seasons`) have the
  NBA's names, so the integrity check works on both catalogs (without the
  NBA's rule that game ids encode the season). `team_seasons.torvik_team`
  joins ESPN's teams to torvik's, from a crosswalk made once by name and
  record and checked against every torvik team-season. ESPN summaries are
  kept without their news, videos and betting odds, more than half of
  each response, which break the "keep raw responses" rule but don't
  describe the game
